4.1.Real-time Live Tracking Architecture
ฝั่ง Rider อัปเดตพิกัดเข้าระบบ (Ingress): เลือกใช้ MQTT (Message Queuing Telemetry Transport)

เพราะว่า MQTT เป็นโปรโตคอลที่เบามาก (Lightweight) มีขนาด Header เล็ก (เพียง 2 bytes) 
และประหยัดพลังงานบนโทรศัพท์มือถือของ Rider ได้ดีที่สุด รวมถึงรองรับระบบเครือข่ายอินเทอร์เน็ตที่ผันผวนบ่อยขณะขับรถได้ดีผ่านกลไก 
Keep-Alive และ QoS (Quality of Service) Level 0 หรือ 1 
(พิกัดส่งไม่สำเร็จรอบนี้รอบหน้าก็อัปเดตใหม่ได้ ไม่จำเป็นต้องหน่วงระบบเพื่อรอส่งซ้ำ)

ฝั่งลูกค้าดึงพิกัดไปแสดงผลแบบ Real-time (Egress): เลือกใช้ WebSocket
เพราะว่า WebSocket ทำงานได้ดีที่สุดบน Web App และ Mobile App ของฝั่งลูกค้า 
โดยระบบหลังบ้านจะนำพิกัดจาก Rider ที่สตรีมเข้ามาผ่าน MQTT Broker ไปกระจายต่อให้ลูกค้า 10,000 คนผ่านเทคนิค Pub/Sub (Publish/Subscribe) 
ลูกค้าที่เปิดดูหน้าร้านหรือหน้าติดตามสถานะอาหารจะทำสัญญารับข้อมูลเฉพาะห้องออร์เดอร์นั้น ๆ (Room/Channel) 
แบบ Full-Duplex (สองทางแบบทันที) ทำให้เห็นไอคอนรถขยับบนหน้าจอได้อย่างราบรื่น


4.2.Storage Strategy: กลยุทธ์การจัดเก็บฐานข้อมูล (Database Strategy)
พิกัดเปลี่ยนทุก 2 วินาที จาก Rider 2,000 คน หมายความว่าจะมีอัตราการเขียนข้อมูล (Write Load) อยู่ที่ 1,000 Requests/Second 
หากบันทึกลงฮาร์ดดิสก์ตรง ๆ (SQL/NoSQL) จะทำให้ Disk I/O เต็มและระบบจะค้าง

    ตัวเลือกที่ถูกต้อง: In-memory Database (เช่น Redis)
กลยุทธ์การจัดเก็บ (Caching & Buffer): พิกัดสดที่วิ่งเข้ามาทุก 2 วินาทีจะถูกเขียนลง Redis โดยใช้โครงสร้างข้อมูลประเภท 
Redis Geospatial (Geo Hashing) เช่น คำสั่ง GEOADD ซึ่งช่วยให้ระบบเก็บพิกัดละติจูด/ลองจิจูดใน RAM ได้อย่างรวดเร็ว 
(ความเร็วระดับ Sub-millisecond) และสามารถค้นหา Rider ที่อยู่ใกล้เคียงผ่านคำสั่ง GEORADIUS ได้ทันทีโดยไม่สร้างภาระให้ฮาร์ดดิสก์

การจัดการข้อมูลระยะยาว (Fallback to Cold Storage):
    ข้อมูลใน Redis จะทำหน้าที่เป็น "พิกัดปัจจุบัน (Current Location)" เท่านั้น และตั้งเวลาหมดอายุ (TTL) ไว้สั้น ๆ
หากต้องการเก็บข้อมูลพิกัดไว้ประมวลผลย้อนหลัง ยอดระยะทาง หรือใช้ตรวจจับการทุจริต (Fraud Detection) 
ระบบจะไม่สั่งเขียนทีละรายการ แต่จะใช้ Message Queue (เช่น Apache Kafka หรือ RabbitMQ) ทำหน้าที่คอยซับแรงข้อมูล (Buffering) 
แล้วใช้ Worker ดึงข้อมูลแบบมัดรวม (Bulk/Batch Insert) ไปบันทึกลง NoSQL Database (เช่น MongoDB, TimescaleDB, หรือ Cassandra) 
ทุก ๆ 1-5 นาที เพื่อถนอม Disk I/O
